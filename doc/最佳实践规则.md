# Multica 最佳实践规则

> 日期：2026-08-04
>
> 适用范围：Multica 研发小队的编组、智能体配置、项目管理、Issue 协作、产物交付和人工通知。

本文只保留可复用规则。UOS AI 开发小队的具体角色和流程见 [uos-ai开发小队实践.md](./uos-ai开发小队实践.md)。

## 1. 小队设计

### 1.1 按交付阶段设置角色

每个智能体负责一个明确的交付阶段；没有独立产物或边界的职责不单独建智能体。

> 工程依据：单一职责原则要求一个执行单元只承担一种主要变化原因。按需求、方案、实现和审查分工，可以降低职责冲突，并为每个阶段设置明确的输入、产物和完成条件。

### 1.2 单一能力优先做成 skill

代码提交、安全扫描等单一能力优先做成 skill，由相关智能体组合使用。

> 代码依据：Multica 的 `writeSkillFiles` 会把绑定能力写入独立的 `SKILL.md`；skill 可以脱离角色指令单独加载。参见 `multica/server/internal/daemon/execenv/context.go`。

### 1.3 小队指令只写路由规则

小队指令只描述阶段顺序、派发条件和人工关口，并保持简短。

> 代码依据：`buildSquadLeaderBriefing` 将 `squad.instructions` 追加到队长指令；daemon 仅在 claim 的智能体等于 `squad.LeaderID` 时注入。参见 `multica/server/internal/handler/squad_briefing.go` 和 `daemon.go`。

### 1.4 所有角色使用同一流程基线

入口角色确定 full-sha 后，后续角色只读取和传递，不自行更新基线。

> 工程依据：以不可变 commit SHA 作为基线符合可复现构建原则，可以让方案、实现、审查和 patch 指向同一份源码，避免不同 runtime 因拉取时间不同产生基线漂移。

## 2. 智能体指令

### 2.1 保持指令精简

自定义指令保持精简，建议控制在 1000 字以内，只保留角色定位、执行方式和必要约束。

> 代码依据：Multica 自动注入的平台信息已经超过 3000 词，运行时还会装配 Agent Identity、Workspace Context、Project Context、Workflow、Skills、Tools 和 Output 等多个区段。自定义指令只是完整上下文的一部分；指令过长会继续扩大上下文、分散模型注意力，使关键要求更难被稳定识别和执行，并挤占任务、代码和工具结果的可用空间。参见 `multica/server/internal/daemon/execenv/runtime_config_sections.go`。

### 2.2 使用四段式结构

指令统一采用“角色 → 专长 → 工作风格 → 约束”四段式。

```md
角色：<角色名称与定位>

专长：<负责解决的问题和核心产物>

工作风格：
- 阅读 Issue、评论和上游产物。
- 确认并遵守锁定的流程基线。
- 完成工作、验证结果并发布约定产物。
- 完成、阻塞或请求确认时回交路由。

约束：
- 不越过职责和已审核方案边界。
- 不自行更换基线或跳过人工关口。
- 不直接派发下一角色。
```

四段式的主要好处：

- 角色和专长明确职责范围。
- 工作风格明确输入、动作和产物。
- 约束明确停止条件和禁止事项。
- 统一结构便于比较、评审和维护。

> 工程依据：结构化信息遵循信息分组和关注点分离原则。标题、列表和单一动作短句可以减少规则之间的歧义；陈述句或祈使句配合主动语态，能明确动作主体和预期行为。

### 2.3 人设与能力分开配置

instructions 定义角色行为，skill 定义可复用能力。

> 代码依据：`writeAgentIdentity` 将 agent instructions 写入身份区段；`writeSkillFiles` 则把能力写入独立的 `SKILL.md`。两者在运行时使用不同装配路径。参见 `runtime_config_sections.go` 和 `context.go`。

### 2.4 名称和描述只做识别

名称保持简短，描述只写一句用途；行为规则必须写入 instructions。

> 代码依据：daemon 的 `TaskAgentData` 不包含 agent description，而 `writeAgentIdentity` 会写入 agent name 和 instructions。参见 `multica/server/internal/handler/agent.go` 与 `runtime_config_sections.go`。

### 2.5 本地智能体负责环境验证

本地构建、运行和设备相关检查可以交给本地 runtime 智能体，并将结果回写原 Issue。

> 工程依据：验证应尽量在接近真实运行环境的位置执行。将环境相关验证放到本地 runtime，可以减少远端环境差异；将结果回写 Issue 则保留统一的审计记录。

## 3. 项目管理

### 3.1 项目描述只写持久背景

项目描述写目标、架构和长期约束，不写临时进度或任务步骤。

> 代码依据：`writeProjectContext` 会把 project description 写入该项目任务的 `Project Context`。临时信息写入后会持续进入后续任务。参见 `multica/server/internal/daemon/execenv/runtime_config_sections.go`。

### 3.2 项目按管理范围拆分

项目按业务条线或模块细分，不要求与代码仓库一一对应；看板优先使用列表视图。

> 工程依据：看板管理强调限制信息量和在制品数量。缩小项目管理范围可以降低扫描成本，使状态、归属和等待项更容易识别；代码仓库是源码边界，项目是工作管理边界，两者不必相同。

### 3.3 具体资料放入项目资源

仓库、设计稿和参考文档放入项目资源，项目描述只解释它们的背景。

> 代码依据：`writeProjectContext` 分别渲染 ProjectDescription 和 ProjectResources，并提示智能体只在相关时打开资源。参见 `runtime_config_sections.go`。

## 4. Issue 与交付

### 4.1 一个 Issue 承载一条完整需求

一条需求在同一 Issue 内完成细化、设计、实现、审查和验收。

> 工程依据：端到端可追溯性要求需求、实现和验收能够沿同一工作项关联。一个 Issue 混入多条需求会扩大 WIP 和审核范围；按文件或技术层拆分则会增加跨 Issue 协调。

### 4.2 同一问题继续原 thread

问题未处理完时在原 thread 追加评论，不重复开启讨论入口。

> 工程依据：保持讨论局部性可以减少信息检索和上下文重建。多个并行 thread 会增加阅读路径和遗漏前置结论的概率。

### 4.3 产物先持久化再交接

实现进入审查前必须形成 WIP commit 或实现 patch；验证 patch 必须基于明确的 base SHA。

> 工程依据：可恢复交付要求工作产物脱离临时 working tree 后仍可重建。commit 或 patch 提供稳定边界，base SHA 则保证接收方可以确认适用源码版本。

### 4.4 patch 使用 gzip 压缩包

实现 patch 和验证 patch 统一使用 `.patch.gz` 交付，并注明 base SHA、patch 类型和应用命令。

> 工程依据：明文 patch 经过文本通道时可能被转义、内容检测或过滤规则改写；压缩封装可以减少逐行文本处理对原始差异的影响。接收方解压后仍应检查 patch 和基线，确保交付完整。

### 4.5 人工保留最终决策

需求、方案、真实环境验证和远端合入由人最终确认。

> 工程依据：阶段门禁用于在高成本动作前确认责任和风险。产品意图、架构边界、真实环境结果和发布权限都包含组织责任，不应仅由自动化执行者自行批准。

## 5. 平台操作与通知

### 5.1 通过聊天调用 Multica CLI

项目资源、智能体配置和 skill 绑定等平台设置优先通过聊天完成。

> 代码依据：Multica 运行时提示词包含“Always Use CLI”等操作区段，并向智能体提供平台命令入口。参见 `multica/server/internal/daemon/execenv/runtime_config_sections.go`。

### 5.2 只在人工节点发送通知

需求审核、方案审核、人工验证、阻塞和合入确认需要通知；纯智能体流转不通知。

> 工程依据：异常驱动通知可以降低持续盯盘成本和告警疲劳。Issue 保留正式状态和产物，企业微信只承担提醒作用，符合记录系统与通知渠道分离的原则。
